# 04 — Planets, Terrain, Atmosphere, and Planetary Movement

**Scope:** Rodina 1.6.2's planet data model, terrain-generation algorithms that are visible in shader source, altitude/gravity/atmosphere behaviour, landing, LOD parameters, and large-world precision. Static analysis only.

**Confidence tags:** `[C]` confirmed in readable source, `[I]` inferred from constants/API shape, `[U]` engine-side or unverifiable.

---

## 1. One-paragraph summary

Rodina's planets are **data-authored spheres** (`PlanetDef` tables) with radii of 4,000–10,000 km and 200 km atmospheres, orbiting at game-scaled AU distances. Surface height is generated by a family of cubesphere functions in HLSL: a baked height map plus a baked normal map per planet, evaluated from domain-warped Perlin and Voronoi fields, with separate plateau, mountain, hole/crater and lowland bands. The visible terrain shader blends up to eight authored material features using six multiplicative gates (altitude, latitude, surface normal, four feature masks), with distance-driven band widening and four texture tiers. Mesh LOD, terrain collision, and height queries are engine-side; only the height/normal *bake* and material blending are visible. Landing is not a special mode: it is declared when the hull's last terrain contact is within 1 m of the current surface distance and speed is below 4 m/s. The rendering has no physical atmosphere scattering; it is an analytic angular haze/sunset model.

## 2. Planet data model

### 2.1 Units and scale

`Scripts/EGConstants.lua`:

| Constant | Value | Line |
|---|---|---|
| `AU` | `150e9 * 0.05` = **7.5e9 m** (game-scaled AU) | 4 |
| `SunRadius` | `700e6 m` | 5 |
| `EarthRadius` | `6.3e6 m` | 7 |
| `StellarScale` | `1e11 m` | 20 |
| `LightSecond` | `2.99792458e8 m` | 22 |

A game AU is 7.5 million km, one-twentieth of a real AU. Planet radii are authored directly in metres (`10000 * 1000` = 10,000 km). This is the same order as Starfall's default 6,378 km radius, so the two projects are visually/scalably comparable even though Rodina's travel speeds are far higher.

This is a useful design detail: **the tutorial begins on a small asteroid, not a planet**, so the first flying experience is low-gravity and close to the ground.

### 2.3 Orbital and rotation data

Each planet carries:

- `OrbitRadius`, `OrbitTime`, `OrbitInclination` (`EGVector` of Euler angles).
- `RotationTime`, `Tilt` (`EGVector`).
- `Parent` (e.g. `Perun.Parent = "Zorica"`, `Zosia.Parent = "Danica"`).
- `StarLight` / `StarPosition` for stars.

`EGSceneSolar` sets only time deltas, not positions:

```lua
ZoricaYearTime = 60 * 60 * 10   -- 10 hours per orbit
ZoricaDayTime  = 60 * 30        -- 30 minutes per rotation
self.OrbitTimeDelta    = 2π / ZoricaYearTime
self.RotationTimeDelta = 2π / ZoricaDayTime
```

(`EGSceneSolar.lua:5-7`, `:83-84`). The engine integrates positions from these deltas, `OrbitTime`/`RotationTime` multipliers, inclination and tilt `[I]`. There is no Kepler solver, no n-body physics and no orbital state saved per frame; the orbit is an authored animation. The `EGSceneSolar` code also pauses orbit/rotation while a menu is open (`:43-50`).

**Implication for Starfall:** do not build a real ephemeris if the goal is Rodina-like play. A deterministic `orbit_angle = f(orbit_radius, period, epoch)` is enough and is save-friendly.

## 3. Terrain generation

### 3.1 What is visible and what is not

| Layer | Where | Status |
|---|---|---|
| Height function `GetPlanetHeight(unitDir)` | HLSL `Shaders/PlanetPerun.h`, `PlanetVeles.h`, `PlanetJarilo.h`, `PlanetMorena.h`, `PlanetAsteroid.h` | **readable algorithm** |
| Feature masks `GetPlanetFeatures` | same files | readable |
| Cubesphere warp and bake | `Shaders/Planet_Common.h` | readable |
| Height/normal texture resolution | `PlanetDef.DiffuseMapSize` (typically 1024) | data |
| Mesh generation, chunk LOD, tessellation, collision | engine | **not available** |
| CPU height query | `Engine:GetHeightAtLocalPos(localDir)` | API only |
| Terrain material blending | `Shaders/RodinaTerrain.fx` | readable |
| Terrain feature authoring | `Scripts/Data/EGEditorData.lua` `PlanetTerrains` | readable data |

The shaders are bake shaders (`PSPlanetHeights`, `PSPlanetNormals`), not per-frame tessellation code. `PlanetPerun.fx` is a tiny pixel shader that writes `GetPlanetFeatures(coord)` to a colour target (`PlanetPerun.fx:6-18`). So the source tells us the *shape* of the height field, but not how the engine turns it into chunks or collides against it.

### 3.2 Cubesphere

`Planet_Common.h:99-112`:

```hlsl
result.x = x * sqrt(1 - y²/2 - z²/2 + y²z²/3)
result.y = y * sqrt(1 - z²/2 - x²/2 + z²x²/3)
result.z = z * sqrt(1 - x²/2 - y²/2 + x²y²/3)
return normalize(result)
```

This is the standard "spherified cube" mapping. `GetUnitPlanetCoord` adds a half-texel offset and divides by `TargetSize - 1` so the bake covers the exact face edge (`:115-132`). Six faces are defined by `LowerLeft/LowerRight/UpperLeft/UpperRight` in a constant buffer (`:19-33`).

Height is baked to RGB (one scalar repeated three times — the author notes this waste at `:142`), and normals are baked by a **five-tap finite difference in cube-face space**, with a fixed `delta = 0.00015` and four cross products (`:161-211`). This is a good reference for Starfall's own height/normal bake or CPU normal calculation: five evaluations per texel, one central and four neighbours.

### 3.3 The height-field grammar

For the data-driven worlds (Perun, Jarilo, Asteroid), `GetPlanetFeatures` produces a four-channel vector `(base, plateau, mountainMask·mountains, holes)` (`PlanetPerun.h:91-94`):

1. **Domain warp.** Two derivative-noise fields offset the sphere position; the result is re-normalised. Separate warped coordinates are used for the mask, the base and the mountains (`PlanetPerun.h:52-59`).
2. **Base.** `Voronoi2(baseCoords, scale/jitter, strength)` gives a cellular lowland pattern (`:61`).
3. **Plateau mask.** `FractalPerlin` remapped by `Analogue` (`:79-80`).
4. **Mountain mask and mountains.** A Perlin mask times a second Perlin field (`:82-86`).
5. **Holes/craters.** A four-branch classifier on a Perlin field produces smooth-rimmed basins (`:64-77`).

`GetPlanetHeight` then remaps each channel, cross-fades them (`base = lerp(base, 0, plateau)`, `base = lerp(base, 0, mountains)`, `mountains = lerp(mountains, 0, holes)`) and sums three weighted fractal components (`PlanetPerun.h:103-150`). The result is a height in metres relative to the planet radius.

The other worlds:

- **Jarilo** adds a plateau domain warp, dune and hole-override blocks (`PlanetJarilo.h`).
- **Asteroid** adds `PlanetGenConstants[104]` as a flat radius offset and composes mountains additively, so an asteroid need not be spherical (`PlanetAsteroid.h`).
- **Morena** is hand-coded: a plate/crack model where `bigCrackMask = platePerlin - cos(clamp(30·(a·crackCoord.z + b·crackCoord.y), ±8π))` turns a Perlin field into periodic plate boundaries; height is `14,000 + plateau·(±1,000) - cracks·15,000 + mountains·30,000·fractal` plus a quantised dune ripple (`PlanetMorena.h:47-130`).
- **Veles** is the same family with a Voronoi base and fixed 20,000/15,000 amplitudes (`PlanetVeles.h`).

This is the strongest conceptual lesson in the planet system: **one height-function interface, several authored parameter sets, and hard-coded functions when tuning wins**. Starfall can implement the same split with a `TerrainProfile` resource: base/plateau/mountain/crater weights, noise scales, warp strengths, colour palettes, and optional custom height functions.

### 3.5 Terrain LOD and texture tiers

From `RodinaTerrain.fx:21-37` (verbatim constants, with the comment "HACK: These values mirrored in EGRenderGroup.cpp"):

```
TexDistDetail            500 m
TexDist                5,000 m
TexDistDistance       50,000 m
TexDistVeryDistant    2,000,000 m
TexDistVeryDistantClose 200,000 m
TexDistVeryDistantFar   100,000 m

PlanetNear   50 km, Near2 750 km, Far 750 km, Far2 18,000 km
(sun/other set) 50 km, 200 km, 350 km, 1,000 km
```

`TerrainFeature` has four texture tiers per feature; with `EG_PLANET_TERRAIN_MAX = 8` a worst-case draw binds 32 albedo textures (`_terrain_constants.h`). The blend for each tier is `saturate((distance - depth) / (distance * 0.5))`, i.e. fade in over half the tier's range (`RodinaTerrain.fx:101-108`). The very-distant tier is deliberately reversed (far→near, `:211`).

`PlanetDef` exposes LOD tuning:

| Planet | `TerrainLODDistanceMult` | `TerrainLODMult` | `TerrainLODExp` | `TerrainDetailAltitude` |
|---|---|---|---|---|
| Zosia / Perun | 1 | 0.15 | 4 | 500 km |
| Veles | 1 | 0.25 | 4 | 400 km |
| Jarilo / Morena | 1 | 0.25 | 4 | 400 km |
| AsteroidLarge | 1 | 60 | 3 | 100 km |
| Asteroid | 1 | 1000 (or 750–1000 by radius) | 3 | 30 km |

(Values from `EGDataPlanets.lua:143-150`, `:264-271`, `:424-427`, `:533-536`, `:709-712`, `:974-978`, `:1235-1239`, `:1332`.)

The meaning of `TerrainLODMult`/`Exp` is not documented; it is engine-side `[U]`. What can be confirmed is that asteroid LOD is tuned three orders of magnitude more aggressively than planet LOD, which matches their much smaller radii and the need for close surface detail.

### 3.6 Terrain material blending

`RodinaTerrain.fx:40-75` gates each authored `TerrainFeature` on:

1. **Altitude** — `length(WorldPos - PlanetCenter)`, band `HeightEdge ± HeightFade·fadeMult`.
2. **Latitude** — `asin(abs(dot(fromCenter, (0,0,1))))`, band `LatitudeEdge ± LatitudeFade·fadeMult`.
3. **Normal** — `acos(dot(fromCenter, normalWorld))`, remapped by `NormalEdge ± NormalFade`, with `NormalTargetLow/High` allowing flat-ground or cliff-specific features.
4. **Four feature masks** — `FeaturesEdge.xyzw ± FeaturesFade.xyzw·fadeMult`.

`blend = altitude * latitude * normal * fx * fy * fz * fw` — a multiplicative AND, no normalisation. `fadeMult = Analogue(distance, 1000, 100000, 1, 4.0)` widens every band up to 4× with distance, a cheap anti-aliasing/LOD trick (`:45`). Features are composited painter-style: `terrainBlend` starts at 1, each accepted feature consumes coverage, and the loop early-outs when coverage is exhausted (`:195-298`). Base colour is cross-faded between ground and space variants by `AltitudeRatio` (`:202-204`).

**This is directly applicable to Starfall.** The current `TerrainNoise` uses continental/mountain/detail/micro layers and vertex colouring. Adding feature *masks* (rock on steep normals, sand at low altitude, snow at high altitude, ice at poles) would materially improve planetary variety without changing the mesh/LOD system.

## 4. Height queries, collision, and landing

### 4.1 Engine queries

The Lua-visible surface APIs are:

| API | Use | Evidence |
|---|---|---|
| `Engine:GetHeightAtLocalPos(localDirection)` | spawn a ground entity at terrain height | `EGPlanet.lua:387` |
| `planet.Engine:GetSurfacePosition(entityEngine)` | project an entity onto the surface; returns `EGPreciseVector` | `EGProxyItem.lua:60,104,155` |
| `engine:GetPlanetDistance()` | distance from entity to surface | `EGVehicle.lua:938`; `EGWorldObject.lua:171` |
| `planet:GetAltitude(entity)` | `distance - Radius` | `EGPlanet.lua:117-121` |
| `planet:GetAltitudeRatio(entity)` | altitude / atmosphere altitude | `:124-129` |
| `planet:GetDistanceToAtmosphere(entity)` | max(altitude − atmosphere altitude, 0) | `:132-137` |
| `entity:IsInWorldspace(planet)` | walk the parent-worldspace chain | `EGWorldObject.lua:285-293` |

`GetSurfacePosition` returns a **precise vector** type distinct from the ordinary `EGVector`; call sites repeatedly copy components into `EGVector` with comments like `-- AWFUL AWFUL HACK: Needed because GetSurfacePosition() returns an EGPreciseVector! Bad!` (`EGProxyItem.lua:197`; `EGGame.lua:826`). This is direct evidence that Rodina maintains a high-precision world position representation and a lower-precision local entity representation.

`GetHeightAtLocalPos` is called exactly once in Lua, for placing a ground enemy group (`EGPlanet.lua:369-417`). The terrain height query is otherwise engine-internal.

### 4.2 Landing

There is no landing gear, no landing pad, and no terrain flattening for the player ship. `UpdateLanding` (`EGVehicle.lua:2009-2047`) uses the last collision distance:

```lua
if surfaceDistance <= TerrainContactSurfaceDistance + 1 and speed < 4.0 then
    hasLanded = true
```

`TerrainContactSurfaceDistance` is recorded in `OnCollision` whenever the hull touches a planet (`:736-737`). The result is a contact-relative test that works on slopes:

- The hull can rest on a slope; the "landed" check follows the contact point, not the ship origin.
- `speed < 4` means a slow slide can still count as landed, but a fast touchdown does not.
- There is no snap, no orientation correction, and no "safe landing" volume. The ship remains under normal physics with friction 0.4 / restitution 0.8; on steep slopes it can slide.
- The only automatic attitude help is roll levelling in atmosphere (`UpdateLevel`), not pitch/roll alignment to the local surface.

This contrasts with Starfall's existing `Ship._collide_with_terrain` + `ground_gap()` support-point method, which is more robust on uneven terrain and is worth keeping (see `08`).

### 4.3 Terrain flattening is for buildings, not ships

`EGBuilding` has `Components = { "Building", "FlattenTerrain" }` and default `FlattenTerrainInnerRadius = 15`, `FlattenTerrainOuterRadius = 150` (`EGBuilding.lua:15-23`). Building subclasses widen the radii (e.g. 100/350 for a 5×5 xeno building, 200/350 for V, `EGDataBuildings.lua:38-120`). The engine's `FlattenTerrain` component blends the height field down to a flat pad inside the inner radius and back to natural terrain by the outer radius `[I]`. This is a key technique for landing-zone variety: **flatten pads around authored structures, not around the player's arbitrary landing point**.

No Lua code flattens terrain for ship landing. If Starfall wants reliable pads at POIs, implement a terrain-modifier layer with the same two radii; do not globally flatten the planet.

## 5. Atmosphere

### 5.1 Data

Each planet carries (example Perun, `EGDataPlanets.lua:229-248`):

- `AtmosphereAltitude` (200 km), `AtmosphereDensity` (1.5), `AtmosphereFriction` (1.0).
- `AtmosphereScatterColor1/2`, `AtmosphereFilterColor1/2` (hue/saturation/value-derived).
- `AtmosphereGroundDistance` (1.5), `StarHalo` (0.05), `SunsetStarHalo` (0.2), `SunsetStarAngleBuffer` (0.2), `SunsetHorizonLimit` (-1.0).
- `TerminatorBegin` (0.2), `TerminatorEnd` (-0.5).
- `Fog` preset name, `BlurOutRadius`, `BlurOutNear/Far`.

Stars use 50,000 km atmospheres and `AtmosphereDamage` (e.g. Zorica `.0333`, "SOLAR RADIATION", particles `ZoricaAtmosphereDamage`) — a gameplay hazard, not just visuals (`EGDataPlanets.lua:19-22`).

### 5.2 Rendering model

`Shaders/_atmosphere.h` is 379 lines and is **not** a Rayleigh/Mie scattering integral. It is:

- One angle from the planet centre: `pointAngle = acos(dot(normalize(WorldPos), -PlanetToCameraDir))`.
- `outHorizonFactor` = remap between planet radius angle and atmosphere radius angle, eased.
- A fixed `0.66 rad` ground band below the horizon.
- `color = saturate(1 - Analogue(AltitudeRatio, 0.25, 1.0, inHorizonFactor, outHorizonFactor))`.
- `depthFactor = Approach(depth / AtmosphereAltitude, 1.0, 5.0)` (rectangular hyperbola).
- `densityFactor = Analogue(AltitudeRatio, 0.5, 1.0, depthFactor, color)`.
- Sunset/halo from the angle between star direction and view, a squared halo, and a horizon factor.
- A 10-sample march only to soften the terminator on the atmosphere shell (`_atmosphere.h:284-335`).

The three full-screen passes are scatter, filter, and blur. The blur output feeds the depth-of-field control, so the limb is blurred as a cheap aerial-perspective cue. There is no wavelength-dependent extinction; sunsets cannot change colour correctly with view angle, only by blending two authored palettes.

**Implication:** Rodina's atmosphere is a *look*, tuned by artists, costing almost nothing. Starfall's current atmosphere is already a shell/visual effect; adding this horizon/sunset palette model is a high-value, low-risk upgrade. A physically based single-scatter integral is a later, optional milestone.

### 5.3 Entry and atmospheric flight

The gameplay side is covered in `02`; the planetary constants that matter are:

- Altitude ratio is measured against `AtmosphereAltitude` (200 km).
- Full "inside" at ratio < 0.5; entry begins at ratio < 1; exit at ratio > 1 (`EGVehicle.lua:991-1017`).
- A 4 s `EntryCompleteTimer` drives effects, auto-level schedule, and music (`:5`, `:1019-1021`).
- Atmosphere resistance is dot(velocity, down) × altitude/speed factor (`:1077-1139`).
- Auto-level is roll-only, scaled by `SurfaceGravity` (`:1152-1198`).
- Planet-specific atmosphere damage uses `AtmosphereDamage`, `AtmosphereDamageStage`, and particles (`EGPlanet.lua:816-832`; `EGVehicle.lua:1040-1074`).

## 6. Gravity and character orientation

- `EGPlanet:GetGravity(target, minGravity)` returns a vector toward the planet centre with magnitude `max(SurfaceGravity, min) / ratio²`, where `ratio = distance / Radius` (`EGPlanet.lua:150-158`). At the surface it equals `SurfaceGravity`; at 2 R it is one quarter.
- Vehicle gravity is added as a local acceleration scaled by `GravityMult * 9.8 * 3.5` (`EGVehicle.lua:1548-1554`). `kGravityMinPlanetGravity = 0.33` prevents tiny bodies from having unusably low gravity for the ship (`:9`).
- The character has its own character-relative physics constants: `GroundGravity = -250`, `AirGravity = -40`, `JumpHeight = 3`, `WalkSpeed = 7.5`, `GroundSpeed = 10` for the player (`EGPlayer.lua:31-74`); xenos use `GroundSpeed = 20` (`EGDataCharacterXeno.lua:70-90`). These are **local character accelerations**, not planet gravity; the engine composes them with the planet frame `[I]`.
- The engine reports `GetCharacterPhysicsContext()` as `"GROUND"`/`"IN AIR"` and `GetMovementModeJetpack()`; Lua uses these for decompression scaling and jetpack fuel (`EGCharacterActor.lua:269-291`, `:372-377`).
- Player upright orientation on a sphere is engine-side. There is no Lua quaternion code for planet gravity; the player's local transform and `CameraOffset = (0,0,1.65)` are the only visible pieces (`EGPlayer.lua:5`). Rodina characters are always upright relative to the planet, not free-rotating.

**For Starfall:** the existing `Pilot._planet_up()` + `_stay_upright()` + `_rest_on_terrain()` implementation (`scripts/pilot.gd:280-317`) is an independent, readable version of the same concept. Keep it. The Rodina-specific lesson is the *character-relative* movement constants (ground vs air acceleration, jump height, slope limit) as data, not the engine composition.

## 7. Precision and origin shifting

Rodina exposes three clues:

1. **Two vector types.** `EGVector` (ordinary float) and `EGPreciseVector` (returned by `GetSurfacePosition`, accepted by `SetPlanetPosition`). Lua call sites explicitly downcast with "AWFUL HACK" comments (`EGProxyItem.lua:113,141,197`; `EGGame.lua:826`).
2. **Planet-local coordinates.** Most entity positions are relative to the current planet; `GetPlanetPosition` / `SetPlanetPosition` move between planet-local and scene space (`EGVehicle.lua:630-640`; `EGGame.lua:822-843`).
3. **Nested worldspaces.** `IsInWorldspace` walks `GetParentWorldspace()` (`EGWorldObject.lua:285-293`), so a planet can be inside a star system, which can be inside a scene.
4. **Shader LOD uses `length(WorldPos)`** as the distance metric (`standard.h:411`), which only behaves for an 18,000 km draw distance if the render origin follows the camera.

Together these strongly imply a **camera-relative / floating-origin renderer with 64-bit world positions and 32-bit local rendering**, but the implementation is in C++ and cannot be confirmed from Lua or shaders `[I]`. There is no Lua origin-shift code.

**Starfall already has an origin-shifting camera** (`scripts/chase_camera.gd:55-63` shifts nodes in the `origin_shift` group after `PlanetCamera.update`). Its planet addon uses `Vector3`/float and a radius in kilometres, with chunk-local positions (`addons/cuberact_planet/scripts/chunk.gd`). That is adequate at Starfall's current scale. If Starfall adds multiple planets and interplanetary distances, the existing shift must be generalised to a hierarchy of frames; do not copy Rodina's C++ precision design without evidence.

## 8. Terrain/landing-zone variety: what Rodina actually offers

Rodina's variety comes from four independent layers:

1. **Per-planet height function and constants** — completely different terrain character (Perun's warped Voronoi/plateau/mountain mix, Morena's cracked plates, Veles's Voronoi base, asteroid chunkiness).
2. **Per-planet palettes and atmosphere** — `PlanetFeatureColor1a/1b/2/3/4`, scatter/filter colours, fog, terminator.
3. **Per-planet terrain material features** — 3–6 authored `PlanetTerrains` sets with altitude/latitude/normal/feature-mask rules and four texture tiers.
4. **Authored surface structures with terrain flattening** — mines and buildings at fixed seeds, with 15–200 m inner pads.

There is **no procedural landing-zone selection, no flat-pad search, no slope scoring, and no "safe to land" query**. The player can land anywhere the hull physically rests. Buildings flatten their own pads. That is the whole system.

For Starfall, the opportunity is to add what Rodina lacks:

- A **site scorer** over the terrain (slope, curvature, distance to POI, biome) to place landing pads and POIs.
- A **terrain modifier layer** with inner/outer radii (copy the concept, not the code).
- **Feature masks** for material variety.
- **Per-biome height profiles** rather than one global noise field.
